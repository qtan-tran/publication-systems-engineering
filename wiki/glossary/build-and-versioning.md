# Build and versioning

This group helps distinguish between producing one book file and building a system that can produce, maintain, and reprint books sustainably.

## The build process

| Term | Explanation |
| --- | --- |
| **Source file** | A file containing content, structure, or design rules used to produce the edition. This is where lasting edits should be made. |
| **Asset** | Supporting components used to make the book: images, maps, logos, covers, or licensed fonts. |
| **Build** | The process of using source files, assets, and typesetting tools to produce a readable product, such as a PDF or EPUB. |
| **Build pipeline** | An organized sequence of work that checks inputs, builds the book, constructs the table of contents and index, validates, and packages the product. |
| **Preflight** | Checking the necessary conditions before building: are the source files complete, are the fonts present, is the configuration valid. |
| **Compilation pass** | One round of the typesetting tool processing the document. Several passes may be needed before page numbers, contents, and references stabilize. |
| **Auxiliary file** | A file generated during typesetting to hold temporary information such as page numbers or reference data. |
| **Clean build** | Rebuilding the edition without depending on old auxiliary files, which may contain stale or corrupted data. |
| **Resumable build** | A process that can continue from a step verified as valid after an interruption, instead of redoing all the work from the start. |
| **Build environment** | The set of software, tool versions, fonts, configuration, and conditions needed to produce an edition. |
| **Reproducibility** | The ability to recreate an edition from stored sources and conditions, at a defined level of correspondence. |

### Why does a book need multiple build passes?

To build an accurate index, the system must know on which page each term occurs. But adding an index or updating the contents can change the pagination again. Building a book is therefore a process with dependencies between steps: the first pass lays out the pages and determines what falls on which page; the entry terms, page numbers, and references are then collected to build the lookup information; further passes inject the lookup information and recompute the pagination; finally the system checks that page numbers and references no longer change unexpectedly. It is not necessarily a one-shot conversion from text to PDF.

## Versions and baselines

| Term | Explanation |
| --- | --- |
| **Version** | A defined state of content, source code, or an edition at one point in time. |
| **Baseline** | The version chosen as the basis for comparing and evaluating later changes. It is not necessarily the newest version. |
| **Snapshot** | A stored capture of the state of a project at one point, for checking or restoring that state. |
| **Patch** | A set of changes intended to address one specific problem or group of problems. |
| **Changelog** | The record of meaningful changes between versions and the reasons for them. |
| **Release candidate** | A version prepared for validation before it can become an official release. |
| **Freeze** | Temporarily stopping changes to a defined scope in order to enable validation and avoid unnecessary edits. |
| **Rollback** | Returning to a stored state when a new version causes serious problems or fails the standard. |
| **Continuation note** | A short document recording the current state, completed work, open problems, and the starting point for the next phase. |

The baseline deserves special attention: without a clear comparison state, one cannot judge whether a change is an improvement or a defect at all.

## Packaging and archiving

| Term | Explanation |
| --- | --- |
| **Artifact** | The concrete file or product generated by the process: a PDF, a validation report, a map, or a source bundle. |
| **Project bundle** | The set of source files, assets, configuration, and documents packaged as one unit that can be stored or transferred. |
| **Public bundle** | A document bundle prepared for public sharing, containing only components appropriate for licensing, privacy, and release scope. |
| **Access-restricted bundle** | A bundle containing internal information, assets, or records that must not be published. Calling a bundle restricted does not by itself secure it; proper custody is required. |
| **Archival bundle** | A bundle kept to preserve the production record, for future validation, restoration, or reprinting. |
| **Release bundle** | The set of products prepared for release; it does not necessarily contain the full history and internal documents of the project. |
| **Artifact manifest** | A structured list of the files in a bundle, with the necessary information such as name, version, role, or checksum. |
| **Checksum** | A value computed from the data of a file to detect whether the file changed or was corrupted relative to the reference copy. |
| **Integrity check** | Verifying that a file or bundle is not missing, broken, or unexpectedly changed. |
| **Maintainability** | How easily and safely a publishing system can be repaired, updated, or further developed. |

A complete project bundle contains: source content (translation, apparatus, bibliography), assets (cover, maps, licensed images), typesetting configuration, the PDF edition, validation reports, the artifact manifest with checksums, and a continuation note.

In one real production project, the working directory at some point no longer held the complete source files, and the project had to be restored from a previous archival bundle. The lesson: a working directory is not a substitute for a durable archival record. A book that exists only as a PDF may still be readable, but future correction and reprinting are limited if the production sources are gone.

## Metadata and technical properties of electronic books

Metadata rarely appears on the book page, but it is essential for identifying, managing, finding, and storing editions.

| Term | Explanation |
| --- | --- |
| **Metadata** | Data describing a document: title, author, translator, language, publication date, licensing, and version. |
| **XMP (Extensible Metadata Platform)** | A standard framework for storing structured metadata inside a document, including PDFs. |
| **Document language** | The declaration of the main language of the document, which lets reading and processing software behave appropriately. |
| **Persistent identifier** | An identifier designed to keep a document recognizable over long periods, for example a DOI or an ISBN in its various roles. |
| **Font resource** | Data about fonts used or declared by a document. A listed resource does not necessarily appear in the visible content. |
| **Text extractability** | The ability to obtain the text of an electronic document for searching, copying, or processing by other tools. |
| **Accessibility** | The degree to which a document can be used by people with different access needs, including screen-reader and assistive-technology users. |
| **PDF/A** | The family of PDF standards designed for long-term document archiving. |
| **PDF/UA** | The standard family defining technical requirements for PDF accessibility. |

XMP differs from what is printed in the book: one edition has a layer of information the reader sees on the cover and title page, and a machine-readable layer such as document title, author, language, and status. Having full XMP metadata, a language declaration, and embedded fonts are useful technical properties, but they do not by themselves prove that a document meets PDF/A or PDF/UA; those standards have their own validation requirements.
